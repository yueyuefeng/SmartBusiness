# 12 架构决策记录

ADR-001–014 均为“建议，待对应 PoC 或业务验证”。ADR-015 已用于本轮离线行业验证内核，不代表生产技术栈变更。

|编号|决策|考虑的替代|理由与代价|验证/重议条件|
|---|---|---|---|---|
|ADR-001|模块化单体起步|立即微服务 / 无模块单体|降低分布式运维成本，同时保持领域边界；需主动验证依赖纪律|独立团队/伸缩/隔离要求有实证时拆服务|
|ADR-002|Flutter 作为五端客户端候选|分别原生 / Web 加桌面容器|共享界面与交互模型；复杂编辑器和原生插件需额外工作|五端插件、输入法、无障碍和文档体验 PoC 失败时重议|
|ADR-003|Java + Spring 领域模块|Kotlin / .NET / TypeScript|候选长期业务建模与事务栈；团队能力未确认|技术团队与原型结果确定语言及兼容版本|
|ADR-004|PostgreSQL + Outbox/Inbox|同步跨模块强事务 / 提前消息集群|初期实现可靠事实传播；需处理重复、乱序和重放|数据库作业吞吐或故障隔离不足时引入消息代理|
|ADR-005|官方渠道适配器 + 能力矩阵|全平台通用收发接口 / 逆向客户端接管|避免伪造不具备的权限和语义；必须逐渠道开发与验收|官方接口变化或新账号能力获准时更新|
|ADR-006|AI 建议与授权命令分离|模型直接写库和外发|保留业务规则与人工责任；交互步骤增加但可审计|有限低风险自动化须有明确策略、预算和可撤回性|
|ADR-007|需求、合同、BOM、内容、报告快照不可变|覆盖式版本更新|支撑争议处理和可复现验证；存储与更正流程更复杂|仅草稿可覆盖，正式版本不放宽|
|ADR-008|以完整利润闭环作为 P0|先把每个模块做完整再连接|尽早验证业务价值；初期大量人工导入/回填|试点显示某手工步骤是主要瓶颈时优先自动化|
|ADR-009|多租户边界前置，部署方式后定|先单租户无隔离后补|避免后续改造数据边界；增加权限与作业测试工作|对性能、客户隔离要求验证后选择共享库或独立库|
|ADR-010|内容发布与会话发送分开|一个万能消息对象|权限、审核、撤回和统计语义不同；有少量共用适配基础设施|仅共享凭据、安全和重试基础组件|
|ADR-011|经营核算与法定财务解耦|自建完整会计总账|聚焦闭环、保留来源与口径；依赖财务系统或专业人员核对|正式提出财务产品需求后单独建模|
|ADR-012|CAD/PLM/WMS 先集成|重建工程绘图、制造与仓储系统|控制范围并沿用专业工具；需解决外部 ID 与版本映射|现有工具不足且业务收益明确再扩展|
|ADR-013|只读 Analytics 与源域事实分离|实时跨库任意联表|明确刷新和口径，减少越权；需投影重建机制|实时度需求需通过成本和一致性权衡|
|ADR-014|ESG 框架和方法版本化|一张全行业 ESG 通用表|支持不同边界、期间和重大性方法；数据治理工作更细|实际披露要求与专业复核决定启用的规则包|
|ADR-015|Python 标准库实现双行业可执行规格|立即搭建完整 Java/Flutter 工程|先验证业务规则与盈利边界，不改变生产选型，增加未来迁移成本|本次已实现并本地测试40项；正式开发时迁移为后端契约测试|
