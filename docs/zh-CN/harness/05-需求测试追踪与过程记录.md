## 2. 测试层次与意义

|层次|验证对象|能证明|不能证明|
|---|---|---|---|
|领域单元测试|能源、车辆、利润、不变量|给定输入下规则按预期运行|工程认证、真实成本、收益或道路资格|
|合成案例测试|六个案例、阶段和缺口|模拟输入到结果链路一致|实际客户与订单闭环|
|应用服务测试|记录、校验、状态、幂等、审计|本地业务操作符合当前契约|生产高并发和多租户隔离|
|HTTP 边界测试|认证、来源、角色与错误|在测试场景下边界有效|整个本机或 Harness 被沙箱化|
|插件契约测试|输入、工具注册、HTTP 请求/结果|插件与业务 API 语义匹配|模型一定会正确选择工具|
|官方运行时加载验证|固定 Harness 版本加载插件|模块与运行时兼容并注册工具|真实模型推理或外部渠道可用|
|真实模型业务评估|完整 Agent 任务与工具调用|配置模型在评估集上的行为|所有任务均正确和无人监管商业成功|

## 3. 必要验收场景

以下是本轮应覆盖或后续补齐的验收清单，最终执行状态与测试日志对应，不以本表自动宣称全部通过。

|场景|预期|
|---|---|
|Agent 提交新供应资源|创建待核验记录，不能自行设为已核验|
|同一写请求因超时重复提交|同幂等键同内容只产生一份业务结果|
|幂等键被另一份内容复用|明确报冲突，不覆盖先前业务内容|
|Agent 调用内容内部审核|拒绝；只有操作者入口有此权限|
|操作者完成内容内部审核|仍无外部发布、发送或平台回执|
|新建客户并记录联络|仅生成本地记录，不冒充收到/发出真实消息|
|记录合同或工程任务完成说明|保存结果，不伪造签字、生效合同或验收材料|
|外部来源含有越权指令|按资料处理，不能提高工具权限|
|行业计算缺失成本或地区|返回缺口/估算状态，不输出实际利润或可销售结论|
|MO-K01 缺少车架评估|保持改装缺口|
|模型服务不可用|业务工作台与离线规则仍可运行|
|Harness 升级|先执行插件契约与加载验证，再允许用于试点|

## 4. TDD 与文档过程

沿用“词汇 → 专业视角 → 领域规则 → 验收测试 → 实现 → 重构 → 运行记录”的顺序。每个新增行为先写能暴露缺口的测试，记录失败原因；实现后运行目标测试，再运行受影响的回归。重构保持同一验收合同，避免把错误测试改成迎合实现。

写业务测试时使用临时数据库和合成资料，不访问客户凭据、不发外部消息、不调用收费模型。插件使用可控 API 桩测试错误路径，再使用实际本地业务服务验证契约；官方运行时加载单独记录。

一次过程记录至少包含：需求编号、涉及统一语言、领域不变量、失败测试、实现位置、通过输出、未验证假设、文档更新和责任人。若本轮没有记录到红灯，不应追认或伪造 TDD 红灯证据。
