# 04 完整商业闭环与生产演进

目标是把市场需求和资源转化为可验证利润。Harness 是提高整理和执行效率的手段；完整商业闭环仍需要权威业务记录、真实客户和可核验的交付、成本、回款。

## 1. 从当前切片到完整闭环

|环节|当前能力|下一项实装|闭环验收证据|
|---|---|---|---|
|市场情报|保存带来源的情报记录|授权数据源采集、去重、更新与证据版本|客户问题可追溯到来源和日期|
|需求归类|建立商机与行业类别|问题聚类、需求基线、验收条件和人工归并|需求有客户、场景、重要性及验收方式|
|资源发现|候选资源登记为待核验|RFQ、报价版本、主体/能力核验、匹配评分解释|至少一个供应路径有有效证据|
|商业模式|合成案例的费用与贡献利润规则|模式假设、价格实验、收入类型与风险预算|客户付费意愿和可交付路径有验证|
|决策|查看行业缺口与就绪条件|投入决策、版本审批、停损条件与复盘|责任人明确批准范围、预算和有效期|
|营销|内容草稿、内部审核|渠道素材、发布任务、官方回执和归因|合格线索成本与成交贡献可追踪|
|统一沟通与 CRM|联系人、本地沟通笔记|授权账号接入、会话收发、身份关联和去重|真实消息回执与客户记录准确关联|
|交易与贸易|术语、流程和领域设计|报价、订单、采购、物流、关税与退款|报价与实际履约、费用、回款可核对|
|合同|合同工作项和结果记录|模板、主体快照、条款审阅、义务与电子签署|签署授权、生效版本和义务状态可核验|
|软件施工|软件工作项和结果记录|需求—测试—提交—构建—部署—验收链|功能验收和发布证据关联到订单|
|硬件设计|硬件工作项、行业计算|BOM、CAD/PLM 版本、样机、测试、变更与交付|配置与样机/交付批次证据一致|
|财务与利润|合成案例贡献利润，不是实际净利润|收入、退款、成本、收付、分摊与对账|不缺关键成本，区分毛利/贡献/净利/现金流|
|ESG|ESG 工作项和材料结果记录|边界、期间、指标、活动数据、因子与复核报告|每个声明可追溯口径、来源和复核记录|
|经营复盘|行业模拟阶段与任务结果|漏斗、毛利/现金、售后、质量与实验回流|下一轮决策有经营结果支持|

“形成闭环”的交付标准是至少一个明确范围的实际业务从需求到回款、成本和复盘贯通。拥有所有模块入口，或者 Agent 写出一份方案，均不满足这个标准。

## 2. 双行业首单路径

能源先选择一个家庭项目或商业场址，再选国家/州/城市和商业模式。可以验证付费需求诊断、安装商线索服务或集成销售中的一种；每种模式的责任、成本和交付证据不同。场址资料、设备方案、供应商与安装路线未核实时不承诺工程结果。

出行先选择一个客户群和车型路线。电动自行车、摩托、改装分别形成试点，优先选择能取得真实产品、安装和售后证据的一条路线。改装需要原车与组合适配材料，不能仅凭套件参数开展承诺。

两个试点共用情报、资源、CRM、营销、合同、贸易和利润模块，行业模型保持独立。首单完成后比较访谈转化率、资源核验周期、获客成本、贡献利润、现金回收周期和售后成本；没有成交时记录被证伪的假设，避免将“内容很多”当成商业进展。

## 3. 分阶段交付门槛

|阶段|建设范围|完成门槛|此阶段仍不承诺|
|---|---|---|---|
|P0 本轮本地原型|工作台、SQLite、Harness 工具、六案例|业务 API 与工具离线测试、运行时加载、中文记录|生产多租户、真实外发、商业成功|
|P1 两行业人工辅助试点|选定市场、客户访谈、供应核验、商业实验|每行业一组真实需求证据和一种收费模式实验|在缺监管/工程材料时可销售或可安装|
|P2 第一条交易闭环|报价、合同义务、交付、成本、回款、复盘|真实订单与成本、收款、验收能够对账|自动涵盖所有业务模式和地区|
|P3 正式渠道与营销|一个渠道收发与一个发布渠道|官方账号权限、幂等回调、撤回/失败与审计通过|所有社交软件均能通用接入|
|P4 生产与五端|身份、多租户、部署隔离、备份、Flutter 客户端|真实角色隔离、恢复演练、五端关键流程验证|未实际测试的平台和原生插件能力|
|P5 工程与 ESG 扩展|Git/CI、CAD/PLM、供应链、指标与报告|工程版本和披露数据链可核验并经责任人复核|自动取代工程师、法律或鉴证工作|

顺序可因业务瓶颈调整，门槛不能用“开发完成百分比”替代。每次扩展先增补统一语言、事件推演和验收样例，再写实现。

## 4. 五端方案

当前原生响应式 Web 用于验证交互。生产候选延续 Flutter：Android、iOS、Windows、macOS、Linux（含目标 Ubuntu 环境）共享业务视图和 API 契约，分别验证输入法、附件、通知、后台任务、文档预览和无障碍。原生插件是否覆盖各平台，要通过实际 PoC 验证。

移动端侧重情报采集、客户沟通、现场核验和审批；桌面侧重情报研究、方案比较、合同/BOM/报告处理。模型凭据、渠道密钥和高权限工具不下发客户端。离线优先只缓存授权草稿，提交后以服务端版本和冲突策略为准。

服务端生产候选仍为模块化单体、关系数据库、可靠事件和独立 AI 执行环境。Python 原型保留下来的可执行行业规格应成为新后端的契约测试，而非仅凭人工重写保证行为一致。

## 5. 社交渠道与营销接入

每个平台独立确认官方接口、账号类型、授权范围、地区限制和商业用途；以[既有渠道矩阵](../07-社交渠道与统一沟通.md)记录“文档可用、账号获权、沙箱通过、生产接通”不同状态。本轮没有选定首个平台，不能宣称已统一收发。

统一界面下仍区分私信、客服会话和公开内容发布。生产建立独立发送/发布任务，绑定内容版本、操作者授权、目标账号和幂等键；只有平台回执才能标记相应状态。支付、下单、签署、公开发布和大规模发送须有明确的业务授权策略与可追溯责任。

## 6. Harness 生产化与评估

将 Agent 运行时置于独立运行环境；业务服务只提供用途明确的接口和短期授权。模型、网页、附件和社交内容均不成为权限来源。敏感资料最小化传入模型，来源、保留期和跨境处理策略按选定市场与实际业务确定。

先建立固定评估集：来源冲突、过期报价、缺成本、能源末态不可比、改装缺证据、内容夸大、重复写入、工具超时、恶意来源指令、上下文丢失。衡量任务完成率、事实/引用准确率、越权拦截率、重复写入率、人工复核时间和实际模型费用。

对比“无 Agent 人工流程”和“同一模型/任务的 Harness 流程”，固定数据与评分标准。是否更好应由这些结果决定。升级 Harness 或模型前跑相同评估集；保留已验证版本与回滚路径，不让自动依赖升级直接改变业务执行权限。
