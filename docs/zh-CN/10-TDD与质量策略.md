# 10 TDD 与质量策略

## 1. 开发顺序

针对每一条已确认业务规则，先写行为例和失败测试，再写最小实现使其通过，最后重构并保持测试通过。TDD 的循环依据见 S18；本项目的具体测试层次与门槛如下。

1. 从需求 Rxx 和规则 BRxx 选择最小纵向切片。
2. 业务、测试和开发用中文给出正例、反例、边界值与例外。
3. 先写自动化测试并实际运行，记录失败原因必须是业务行为尚未实现，不能把编译错误或环境错误当有效 Red。
4. 写最小实现，再运行同一测试和受影响测试，记录 Green。
5. 重构模型和接口，复跑相关测试；随后补充持久化/集成层验证。
6. 更新中文需求与变更记录，关联测试、代码和 CI 证据。

当前交付只有设计与验收规格，**没有产品代码、测试运行器、已执行 Red/Green 或通过率**。不能把下面的 Gherkin 文件当成已通过自动化测试。

## 2. 测试层次

|层次|测试对象|首批关键场景|工具候选|
|---|---|---|---|
|纯领域单元|聚合行为与计算策略|需求确认、权重、过期报价、内容版本、利润缺口|JUnit；固定时钟与 deterministic ID|
|应用用例|权限、事务、幂等与错误语义|跨租户拒绝、同键不同请求体、审批并发冲突|JUnit + 可替换 ports|
|数据库集成|真实约束、事务、RLS、Outbox/Inbox|提交后崩溃、重复事件、隔离与乐观锁|Testcontainers + PostgreSQL|
|模块/架构|DDD 边界|禁止循环依赖、内部包访问、领域依赖 SDK|Spring Modulith 验证 / ArchUnit|
|外部契约|Webhook / API / token 状态|验签、乱序、429、401、超时未知、平台版本变化|脱敏夹具 + 供应商沙箱|
|客户端|状态呈现与交互|发送未知、离线冲突、币种、无权限字段不展示|Flutter unit/widget/integration|
|端到端|完整业务价值链|三类生意闭环、退款导致利润与归因更正|五端中分层选择关键路径并保留真机结果|
|硬件|接口、仿真、样机与 HIL|固件兼容、传感/执行器异常、试验可复现|工程测试台与签名记录|
|AI 评测|分类/匹配/抽取/内容建议|证据引用、错分、跨租户、注入、虚构产品参数|脱敏金标集、人工复核和版本对照|

不要把全部业务测试写成 UI 操作；外部 API 的模拟通过仍需真实账号契约验收。财务和 ESG 计算采用精度、单位和更正的性质测试；硬件不可能全由普通单测覆盖。

## 4. 红绿重构记录模板

- 需求/规则/用例：Rxx / BRxx / ATxx。
- 业务例：给定条件、触发动作、期望结果。
- Red：测试文件、实际命令、失败摘要、日志/CI 链接、时间。
- Green：最小实现提交、实际命令、通过摘要。
- Refactor：改进理由、影响范围与回归证据。
- 模型变化：术语、状态机、ADR 与相关文档。
- 限制：未运行平台、不可用凭据、外部能力缺口。

普通文档编辑无需编造红绿循环。开发代码必须遵守以上流程；不得为了提交一次“失败提交”而破坏主分支，Red 证据可以保存在测试日志和 PR 记录。

## 5. 合并与发布门槛

功能 PR 必须关联规则和验收例；实际 Red/Green/Refactor 记录可查；关键不变量有正反例；受影响模块/集成测试通过；敏感路径有权限与失败处理；中文文档同步更新。

覆盖率是发现空白的辅助指标，不设一个取代业务断言的统一数字；所有首期关键规则须有行为测试。针对重复外发、越权、利润和 ESG 错算优先做边界、性质和有针对性的变异测试。

CI 拟分：
- 每 PR：文档和架构检查、领域/应用/数据库集成、客户端单元/组件、协议兼容。
- 夜间或合并队列：关键 E2E、外部沙箱、故障注入、五端构建。
- 发布候选：五端真实运行验收、签名包与升级回滚、备份恢复、渠道授权与额度核查。

发布审批和客户外发仍依据业务授权执行。没有真实测试和构建证据时只可标记“设计完成”。
