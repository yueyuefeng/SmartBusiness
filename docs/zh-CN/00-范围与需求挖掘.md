# 00 范围与需求挖掘

## 1. 目标与边界

SmartBusiness 是连接业务判断和执行证据的协作系统。用户补充后，核心闭环明确为：市场需求情报 → 资源发现与核实 → 商业模式假设与验证 → 营销获客 → 客户沟通与报价 → 合同交易 → 采购/软件/硬件/中介履约 → 收款与成本核对 → 利润复盘 → 再次决策。传统 BI 的看板只是其中一部分。

首要价值假设：减少跨工具信息丢失，降低无证据决策和需求返工，缩短从客户意图到可验收交付的周期。价值假设要用试点数据验证。

|用户明确要求|本次落实方式|
|---|---|
|在指定仓库开展工作|为 yueyuefeng/SmartBusiness 建立中文设计基线|
|设计前整理领域词汇|先形成词汇编号和上下文定义，再分析歧义|
|多领域专家分析后建模|提供多专业视角预分析、冲突裁决建议及真人验证清单|
|DDD 挖掘与设计|统一语言、事件风暴、子域、限界上下文、聚合与不变量|
|开发遵循 TDD|示例优先、红绿重构证据、分层测试和准入条件|
|Android / iOS / Windows / macOS / Ubuntu|一套业务协议、多端体验与分别构建验证|
|社交软件统一沟通|能力矩阵、官方适配器、受限能力降级与消息可靠性|
|所有过程中文记录|需求、研究、模型、ADR、测试和变更记录模板|

本轮范围是需求拆解和系统设计；后续开发按路线推进。没有未经确认就扩展成全功能 ERP、CAD 编辑器、自动法律意见生成器、自动签约系统或全自动投资系统。

## 4. DDD 需求挖掘工作坊计划

1. 收集 2 个成功项目、1 个延期项目、1 次合同变更、1 次数据更正的脱敏材料。
2. 业务人员用自己的语言复述全过程，记录原话、时间、角色和证据；每个词汇有上下文。
3. 对每个名词问“谁拥有、何时产生、何时不再有效”；对每个动作问“为什么允许、何时禁止、失败怎么办”。
4. 用过去式列领域事件，再补命令、执行人、策略、读模型和外部系统。
5. 对“客户、需求、批准、发布、版本、成本”等歧义词进行跨专业分析。
6. 建立限界上下文；用异常流程检验边界，禁止按数据库表或组织部门机械划分。
7. 把关键业务规则写成中文验收例；产品、业务和开发共同确认后进入 TDD。

产物：访谈纪要、词汇变更、事件风暴图、冲突记录、候选模型、验收例。当前只有用户初始陈述和公开资料，未进行真实访谈或工作坊。

## 5. 优先待确认问题

- 高层方向已确认外贸与内贸；还需确定细分行业、首批客户、企业自用还是商业 SaaS，以及私有化需求。
- 首批渠道的具体产品与账号类型：个人微信、企微客服、公众号、WhatsApp Business 等必须分别回答。
- 业务运行地区、数据驻留要求、敏感资料类型与保留期限？
- 软件施工是自建研发协作，还是自动生成代码并发起交付？本稿按前者并保留 AI 辅助理解。
- 硬件重点是电子电路、机械结构、嵌入式还是设备集成？
- ESG 报告的目标读者、报告主体、期间与准则是什么？
- 现有 Git、CAD/PLM、财务、电子签、CRM、客服平台有哪些？
- 团队、预算、预计用户量、每日消息量和首期截止日期？

## 6. 成效度量

新增核心指标：从信号到已验证商业机会的时长、合格资源匹配时长、商业假设验证成本、合格线索转化率、已核对订单贡献利润、退款损失、现金回收周期。利润为可核对的经营结果，不能保证商业成功。

试点前采集两周基线，试点后对相同类型项目比较：消息漏处理率、首次有效响应时长、需求追溯完整率、决策复盘完成率、变更返工工时、交付验收周期、ESG 证据完备率。不得用消息数量或 AI 生成文档数量代替业务成效。
